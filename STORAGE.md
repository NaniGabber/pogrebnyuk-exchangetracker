## Дослід 1. Вплив індексу

Для дослідження було використано таблицю `exchange_rates`.

### Запит для поля з низькою вибірковістю

Поле `asset` містить лише шість можливих значень: `USD`, `EUR`, `GBP`, `JPY`, `XAU`, `XAG`.

Запит:

```sql
SELECT *
FROM exchange_rates
WHERE asset = 'USD';
```

### Без індексу

План виконання:

```text
Index Scan using uq_exchange_rate on exchange_rates
```

Час виконання:

```text
0.210 ms
```

### Після створення індексу

```sql
CREATE INDEX idx_asset
ON exchange_rates(asset);
```

План виконання:

```text
Index Scan using idx_asset on exchange_rates
```

Час виконання:

```text
0.009 ms
```

### Висновок

Після створення спеціалізованого індексу PostgreSQL використовує індекс `idx_asset` замість попереднього індексу. Час виконання запиту зменшився, однак через невелику кількість можливих значень у полі `asset` приріст продуктивності не є критичним.

---

### Запит для поля з високою вибірковістю

Поле `date` містить значно більшу кількість різних значень, тому має високу вибірковість.

Запит:

```sql
SELECT *
FROM exchange_rates
WHERE date = '2026-07-15';
```

### Без індексу

План виконання:

```text
Seq Scan on exchange_rates
```

Час виконання:

```text
0.020 ms
```

### Після створення індексу

```sql
CREATE INDEX idx_date
ON exchange_rates(date);
```

План виконання:

```text
Index Scan using idx_date on exchange_rates
```

Час виконання:

```text
0.007 ms
```

### Висновок

Для стовпця `date` після створення індексу PostgreSQL перейшов від повного сканування таблиці (`Seq Scan`) до індексного пошуку (`Index Scan`). Це підтверджує, що індекси найкраще працюють для полів з великою кількістю унікальних значень.

## Дослід 2. Вплив межі транзакції

Було виконано вставку 20 000 рядків у таблицю `exchange_rates`.

### Варіант 1. Commit після кожного запису

```python
for row in rows:
    session.add(row)
    session.commit()
```

Час виконання:

```text
57.06 s
```

### Варіант 2. Один commit наприкінці

```python
for row in rows:
    session.add(row)

session.commit()
```

Час виконання:

```text
0.74 s
```

Прискорення:

```text
76.7x
```

### Висновок

Використання одного `commit()` наприкінці транзакції виявилося приблизно у 76.7 раза швидшим за виконання `commit()` після кожного окремого запису. Велика кількість транзакцій створює значні накладні витрати на фіксацію змін і синхронізацію даних із диском. Саме тому в репозиторії використовується пакетна вставка даних та спільний `commit()` для всієї групи записів, а не для кожного рядка окремо.

## Загальний висновок

Проведені дослідження показали, що продуктивність роботи з базою даних суттєво залежить як від структури індексів, так і від способу роботи з транзакціями. Індекси дозволяють уникати повного сканування таблиці та пришвидшують пошук даних, особливо для стовпців із високою вибірковістю. Водночас правильне визначення меж транзакції дає значно більший ефект під час масового завантаження даних. Тому при реалізації сховища було використано пакетну обробку записів та мінімальну кількість операцій `commit()`.
