# Висновки щодо тестування

## 1. Використання підходу TDD

Під час розробки проєкту застосовувався підхід **Test-Driven Development (TDD)**. Для кожної нової функціональності спочатку створювався тест, який описував очікувану поведінку системи. Після отримання негативного результату тестування реалізовувався мінімальний код, необхідний для проходження перевірки.

Після реалізації властивості всі відповідні тести були успішно пройдені.

---

## 2. Тестування доменної логіки

Для доменного шару були створені тести перевірки:

- коректності валідації моделей;
- незмінності об'єктів (`frozen`);
- хешованості моделей;
- усунення дублікатів;
- бізнес-правил предметної області;
- нормалізації текстових даних.

Особлива увага приділялася перевірці граничних значень. Наприклад, під час тестування порогових значень використовувалися значення безпосередньо до та після межі, що дозволяє виявляти помилки типу *off-by-one*.

```python
@pytest.mark.parametrize(
    ("salary", "expected"),
    [
        (2999, False),
        (3000, True),
    ],
)
```

---

## 3. Тестування моделей межі

Для моделі `ExchangeRateIn` були реалізовані тести, які перевіряють:

- приймання коректних даних;
- автоматичне перетворення типів;
- нормалізацію значень полів;
- відхилення невалідних даних;
- створення доменних об'єктів.

Приклад перевірки перетворення курсу:

```python
@pytest.mark.parametrize(
    ("raw", "expected"),
    [
        ("41.5", 41.5),
        ("unknown", None),
        (None, None),
    ],
)
```

Такі перевірки гарантують, що всі зовнішні дані будуть приведені до єдиного формату перед потраплянням у доменну модель.

---

## 4. Тестування конвеєра обробки даних

Окремий набір тестів був присвячений конвеєру обробки даних.

Було перевірено:

- підрахунок статистики;
- обробку невалідних записів;
- усунення дублікатів;
- ліниве виконання генераторів.

Особливе значення мав тест лінивості обробки. Він гарантує, що конвеєр не читає більше записів, ніж потрібно споживачу.

```python
taken = list(islice(Pipeline._parse(source, stats), 3))

assert len(taken) == 3
assert consumed == 3
```

Така перевірка захищає систему від майбутніх змін, які можуть призвести до завантаження всіх даних у пам'ять одночасно.

---

## 5. Тестування адаптерів

Для адаптерів читання JSONL-файлів були створені тести обробки пошкоджених даних.

Перевірялося:

- пропускання некоректних JSON-рядків;
- правильне журналювання помилок;
- продовження обробки файлу після виникнення помилки.

Приклад тесту:

```python
rows = list(JsonlSource(path).read())

assert rows == [{"a": 1}, {"a": 2}]
assert "skip malformed line 2" in caplog.text
```

Такі перевірки забезпечують стійкість застосунку до помилок у вхідних даних.

---

## 6. Тестування інтерфейсу командного рядка

Було реалізовано наскрізні тести CLI, які перевіряють поведінку програми під час реального запуску.

Зокрема перевірялася реакція на відсутність вхідного файлу:

```python
with pytest.raises(SystemExit) as exc:
    main()

assert exc.value.code == 1
```

Це дозволяє гарантувати коректне завершення програми та правильне інформування користувача про помилки.

---

## 7. Виявлення та виправлення дефектів

Під час тестування вдалося виявити помилку конфігурації журналювання.

Тест показав, що програма використовує рівень журналювання `ERROR` замість очікуваного `DEBUG`.

Після виправлення конфігурації всі перевірки були успішно пройдені.

---

## 8. Підсумок

У ході роботи було реалізовано багаторівневу систему тестування, що охоплює доменну логіку, моделі межі, конвеєр обробки даних, адаптери та інтерфейс командного рядка. Автоматизовані тести дозволили своєчасно виявляти помилки, безпечно виконувати рефакторинг та забезпечити стабільність роботи застосунку.

Використання TDD разом із контролем покриття тестами суттєво підвищило якість програмного продукту та спростило подальший супровід коду.
